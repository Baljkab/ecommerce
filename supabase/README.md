# Supabase хүснэгтүүд

## Захиалгын сервер API

Захиалга: браузер → `POST /api/orders` → Supabase `submit_order_once` →
`create_order_with_stock`. Next.js сервер Bearer токеныг `auth.getUser`-аар
баталгаажуулж, хаяг, барааны ID, тоог шалгана. Үнэ болон нийт дүнг браузераас
авахгүй. Хэрэглэгчийн токентой тусдаа Supabase client үүсгэдэг; service-role
түлхүүр болон шинэ dependency шаардлагагүй. Бусад хэсэг одоогоор өмнөх
Supabase холболтоо ашиглана.

Ажиллуулах: эхлээд `202610060004_order_stock_.sql`, дараа нь
`202610060006_order_api_idempotency.sql`-ийг SQL Editor дээр ажиллуулна.
Шинэ SQL нь хэрэглэгч + хүсэлтийн дугаараар давхар захиалга үүсэхээс хамгаална.
Ижил дугаар, ижил өгөгдөл дахин ирвэл өмнөх захиалгын ID буцна. Өөр өгөгдөлтэй
бол алдаа өгнө. Захиалга, үлдэгдэл, хүсэлтийн бүртгэл нэг transaction-д байна.
SQL алсын санд автоматаар ажиллуулаагүй.

Браузер баталгаатай хариу аваагүй хүсэлтийн дугаарыг sessionStorage-д хадгална.
Ижил таб дээр ижил захиалгыг дахин илгээх/refresh хийхэд дугаарыг дахин ашиглана.
Шинэ таб эсвэл хадгалсан мэдээллийг устгавал тусдаа хүсэлт болно. SQL wrapper-ийг
нэвтэрсэн хэрэглэгч шууд дуудаж болох ч Auth болон transaction хамгаалалт үйлчилнэ.

`node --test tests/order-api.test.mjs` нь API-ийн auth, validation, RPC хүсэлтийг
орлуулсан HTTP-ээр шалгана. Migration-ийн дараа нэг хүсэлтийг зэрэг хоёр удаа
илгээж ижил ID ирэх, үлдэгдэл нэг удаа хасагдахыг бодит санд шалгана. Үлдэгдэл
хүрэхгүй үед захиалга болон order_requests мөр үлдэх ёсгүй.

## Хэрэглэгчийн захиалгын түүх

Профайл → «Миний захиалга» (`/orders`) хэсэгт нэвтэрсэн хэрэглэгчийн бүх
төлөвтэй захиалгууд шинэ огнооноосоо эхлэн 10-аар хуудаслагдана. Захиалга
бүрийн бараа, тоо, үнэ, хүргэлтийн хаягийг дэлгэж харна. «Шинэчлэх» товч
нь хүргэлтийн одоогийн төлөвийг дахин татна.

`202610050003_admin_orders.sql`-ийн дараа
`migrations/202610060005_user_order_history.sql`-ийг SQL Editor дээр ажиллуулна.
Энэ нь өөрийн захиалга болон барааны мөрүүдийг унших SELECT policy, индекс
нэмнэ. Админы эрх болон бичих эрхийг өөрчлөхгүй. Өмнөх migration-ийн
restrictive policy нь бусдын захиалгыг уншихаас хамгаална.
Алсын санд энэ SQL-ийг автоматаар ажиллуулаагүй.

`node --test tests/user-orders.test.mjs` нь хэрэглэгчийн ID шүүлт,
хуудаслалт, алдааны төлөвийг HTTP орлуулгаар шалгана. Бодит RLS-ийг
батлахын тулд хоёр хэрэглэгчээр тус тус нэвтэрч, зөвхөн өөрийн захиалгаа
харж байгааг болон бусдын захиалга руу шууд хүсэлт амжилтгүйг шалгана.

## Админы захиалга, хүргэлт

`/admin/orders` нь бүх захиалгын бараа, тоо ширхэг, нийт дүн, огноо,
утас, имэйл, хүргэх хаягийг харуулна. 20 захиалгаар хуудаслаж, хүргэлтийн
төлөвөөр шүүнэ. Шинэ захиалга харахын тулд «Жагсаалт шинэчлэх» товч дарна.

Supabase SQL Editor дээр `202610050001_admin_product_management.sql` ажилласан
байх шаардлагатай (`public.is_admin()`). Дараа нь
`migrations/202610050003_admin_orders.sql` файлыг нэг удаа бүхэлд нь ажиллуулна.
Энэ нь одоо байгаа `orders`, `order_items` хүснэгтүүдэд зориулсан migration.
Алсын өгөгдлийн санд автоматаар ажиллуулаагүй.

- `delivery_status`: `pending` (Хүлээгдэж буй), `shipping` (Хүргэгдэж буй),
  `delivered` (Хүргэгдсэн). Шинэ болон өмнөх захиалгууд анх `pending` болно.
  Өмнө хүргэгдсэн захиалгуудын төлөвийг админ зөв болгож шинэчилнэ.
- Өмнөх `status` баганыг өөрчлөхгүй. Хүргэлтийн төлөв тусдаа хадгалагдана.
- Админ бүх захиалга, барааны мөрийг унших эрхтэй. Бусад хэрэглэгч зөвхөн
  өөрийн захиалгыг унших хүрээнд хязгаарлагдана. Өмнөх эзэмшигчийн INSERT,
  SELECT зэрэг policy хэвээр шаардлагатай.
- Төлөв солих RPC нь админ эрхийг сервер дээр шалгаж, зөвхөн хүргэлтийн
  төлөвийг өөрчилнө. Хуучирсан төлөвтэй хүсэлт татгалзана.
- Энгийн хэрэглэгч хүснэгт рүү шууд хүсэлт явуулсан ч хүргэлтийн төлөвийг
  өөрчилж болохгүй. `profiles.role`-ийг хэрэглэгч өөрөө өөрчлөх эрхгүй байхаар
  одоогийн профайлын эрхийн тохиргоог мөн баталгаажуулна.
- Хэрэглэгч `/orders/[id]` хуудсаа дахин нээх/шинэчлэхэд шинэ төлөв харагдана.

Шалгах: `node --test tests/admin-orders.test.mjs`, `pnpm lint`, `pnpm build`.
Тест нь HTTP орлуулгатай; бодит RLS болон SQL гүйцэтгэлийг батлахгүй.
Migration-ийн дараа хэрэглэгчээр захиалга өгч, админаар мэдээллийг харж,
төлөв хадгалан, дахин ачаалахад хэвээр байгааг шалгана. Өөр хэрэглэгчээр
тэр захиалгыг унших, RPC дуудах, хүргэлтийн төлөвийг шууд өөрчлөх оролдлого
амжилтгүй болох ёстой. Хоёр админ нэг хуучин төлөвөөс зэрэг хадгалахад
хоёр дахь хүсэлт алдаа өгч, жагсаалтыг шинэчлэхийг шаардана.

Хэрэглэгчийн өгсөн бүтцэд `cart_items`, `categories`, `products`,
`product_specs` хүснэгтүүд байна. Сагсны зөв нэр нь `cart_items`.
Өмнө бэлтгэсэн `cart_item` үүсгэх SQL-ийг шинэ тохиргооны файлаар сольсон.

## Одоо байгаа холбоосууд

| Багана                     | Холбогдох багана | Эцэг мөрийг устгахад        |
| -------------------------- | ---------------- | --------------------------- |
| `cart_items.user_id`       | `auth.users.id`  | Сагсны мөр устна            |
| `cart_items.product_id`    | `products.id`    | Сагсны мөр устна            |
| `products.category_id`     | `categories.id`  | `category_id` нь NULL болно |
| `product_specs.product_id` | `products.id`    | Үзүүлэлтийн мөр устна       |

`cart_items.id` нь UUID, `product_id` нь bigint, `quantity` нь integer.
`UNIQUE (user_id, product_id)` аль хэдийн байгаа.

## Ажиллуулах SQL

Supabase → **SQL Editor** дээр
`migrations/202609240002_configure_cart_items.sql` файлын агуулгыг
хуулж ажиллуулна. Хэрэглэгч энэ migration-ийг ажиллуулснаа баталсан.
Алсын сангийн RLS тохиргоог энэ өөрчлөлтийн үеэр тусад нь шалгаагүй.
Энэ нь одоо байгаа хүснэгтэд зориулсан migration; хоосон сан үүсгэх SQL биш.

Өгсөн бүтцэд `cart_items`-ийн RLS асаалттай боловч policy байхгүй байна.
Шинэ SQL дараах тохиргоог хийнэ:

- Хэрэглэгч зөвхөн өөрийн сагсыг уншиж, нэмж, өөрчилж, устгана.
- Нэвтрээгүй хэрэглэгчийн сагсны хүснэгтийн эрхийг хасна.
- Нэвтэрсэн хэрэглэгчид SELECT, INSERT, UPDATE, DELETE эрх олгоно.
- `user_id`-ийн анхны утгыг `auth.uid()` болгоно.
- `quantity > 0` хязгаарлалт болон `product_id` индекс нэмнэ.

Одоо байгаа foreign key болон unique хязгаарлалтуудыг хэвээр ашиглана.
Хэрэв `quantity <= 0` мөр байвал SQL бүх өөрчлөлтийг буцааж, алдаа өгнө.
Тухайн мөрүүдийг зөв болгосны дараа файлыг бүхэлд нь дахин ажиллуулна.

## Вебээс унших жишээ

Нэвтэрсэн хэрэглэгчийн Supabase client-аар:

```ts
const { data, error } = await supabase.from("cart_items").select(`
  id,
  quantity,
  product:products(id, name, price, image_url, stock)
`);
```

`products`, `categories`, `product_specs` хүснэгтүүдэд нийтийн унших
policy аль хэдийн байна. Үнэ, нэр, зураг болон үлдэгдлийг `products`-оос авна.
Сагсанд нэмэх нь барааны үлдэгдлийг бууруулахгүй.

`components/CartProvider.tsx` нь нэвтэрсэн хэрэглэгчийн сагсыг
`lib/cart.ts`-ээр дамжуулан `cart_items` хүснэгтээс уншиж, хадгална.
Нэмэх, тоо өөрчлөх, нэг бараа устгах, сагс хоослох хүсэлт бүр
нэвтэрсэн хэрэглэгчийн `user_id`-гаар хязгаарлагдана. RLS нь сервер дээр
мөн эрхийг шалгана. Сагсанд нэр, үнэ, зураг хуулж хадгалахгүй;
тэдгээрийг `products` хүснэгттэй холбон уншина.

Нэвтрээгүй хэрэглэгчийн түр сагс өмнөх `localStorage` түлхүүрээ ашиглана.
Түр сагсыг нэвтрэх үед бүртгэлийн сагстай автоматаар нэгтгэхгүй.
Бүртгэлд хадгалахын тулд нэвтэрсний дараа бараагаа нэмнэ.
Гарах болон бүртгэл солих үед өмнөх хэрэглэгчийн сагсыг дэлгэцээс арилгана.
Амжилтын мэдэгдэл зөвхөн хадгалалт амжилттай болсны дараа гарна.
Хадгалалт бүтэлгүйтэхэд түр сагс руу чимээгүй шилжихгүй, алдаа харуулна.

Ижил барааг зэрэг нэмэх үед unique зөрчлийг дахин уншиж шийднэ.
Тоо өөрчлөх хүсэлт өмнөх тоотой нь харьцуулж бичдэг тул өөр табын
өөрчлөлтийг хуучин тоогоор дарж бичихгүй.

## Шалгах

1. Нэвтэрсэн хэрэглэгчийн client-аар байгаа барааны ID, `quantity: 1` өгч мөр нэмнэ.
2. Ижил хэрэглэгч, бараатай хоёр дахь мөр болон `quantity: 0` алдаа өгөх ёстой.
3. Өөр хэрэглэгчийн client-аар эхний хэрэглэгчийн мөр харагдахгүй,
   өөрчлөгдөхгүй, устахгүй байх ёстой.
4. Өөр хэрэглэгчийн `user_id`-аар мөр нэмэх, өөрийн мөрийн эзнийг солих
   оролдлого алдаа өгөх ёстой.

RLS шалгалтыг SQL Editor-ийн админ эрхээр бус, нэвтэрсэн хэрэглэгчийн
client-аар хийнэ. Локал lint нь SQL болон алсын RLS-ийн ажиллагааг шалгахгүй.

Локал шалгалт: `node --test tests/cart.test.mjs`, `pnpm lint`, `pnpm build`.
Хүсэлтүүдийн тест нь өгөгдлийн сангийн орлуулга ашиглана; алсын RLS-ийг шалгахгүй.
Веб дээр нэвтэрч бараа нэмээд refresh хийх, +/−, устгах, сагс хоослох,
бүртгэл солих үйлдлүүдийг шалгана. Нэмсэн мөр Table Editor → `cart_items`
дотор тухайн хэрэглэгчийн `user_id`, барааны `product_id`-тай харагдах ёстой.
